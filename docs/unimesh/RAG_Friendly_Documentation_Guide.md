## 8. UniMesh 技术文档的受众标记与 RAG 友好化生成规范

UniMesh 项目的文档系统不采用重型“四类目录分类制度”。Aider 不需要把开发过程中产生的所有临时草稿、一次性日志和短期记录都强行归入固定类别。但是，凡是经由人类主管亲自挑选、会长期保留、会进入知识库、会约束 Aider、会影响项目路线、会帮助人类主管理解全局的 Markdown 文档，都必须在文档头部标注“文档主受众”和“知识库用途”，并根据主受众采用合适的写作策略与 RAG 友好化强度。本规范的目标是在不破坏原文档用途的前提下，使文档既能服务 Aider 的受控执行、人类主管的渐进式理解，又能让场外架构师 Agent 通过知识库检索获得绝对自洽、无歧义的分层项目冷记忆。

### 8.1 基本原则：轻量标签，不做重型分类

UniMesh 文档允许且仅允许使用以下四类主受众标签，但这些标签是底层文档元信息，不是强制目录分类体系：

- **Aider-facing**：主要面向代码车间工人 Aider，强调技术细节、执行纪律、严格规范、开发步骤、提示词模板、验收标准和禁止事项。
- **Human-facing**：主要面向人类开发者主管，强调清晰、直观、准确、低阅读负担，用于快速理解项目结构、开发路线、阶段成果、概念关系和设计取舍。
- **Architect-RAG-facing**：主要面向场外架构师 Agent 的知识库检索，强调项目记忆、正式定义、当前任务、历史结论、事实边界、触发问题和使用限制。
- **Hybrid-Control**：同时服务 Aider 执行、人类主管审阅和场外架构师 RAG 检索，通常用于关键控制文档、阶段控制文档、架构控制文档、当前任务文档和参考工程白皮书。

Aider 必须理解：这些标签用于指导写作策略、索引强度和事实边界表达，不要求按四类建立独立目录，也不要求所有文档完整套用同一模板。RAG 友好化不是替代文档主要服务对象，而是在文档中加入稳定、自洽的语义锚点，使场外架构师能够检索并准确理解其事实状态。

### 8.2 何时必须标注文档主受众和知识库用途（控制权完全归人类）

本规范下的受众标记与 RAG 友好化迭代【不作为】Aider 的日常自发行为，Aider 绝无权自行规划、计算或判定文档的记忆动态权重。所有入库决策与第 8 条规范的启动，必须完全服从人类主管的指挥。

以下文档在【人类主管明确下达指令要求进行第 8 条重构、归档或入库】时，必须严格套用本规范：

1. `CONTEXT.md`、`History.md`、`Project_Tree.md`、`UniMesh_Architecture_Plan.md` 等长期控制或总揽导读文档。
2. 主管指定的当前任务文档、阶段控制文档、Aider 执行规范文档。
3. 提炼完成的架构白皮书、源码侦察报告、参考工程分析、路径索引分析文档。
4. 归档的验收矩阵、蓝图驱动开发协议、黑箱 Bug 防御和回归测试规范。
5. 任何主管指定准备进入 Cherry Studio 知识库、供场外架构师长期检索的文档。
6. 任何会长期约束 Aider 后续代码修改、文档同步、蓝图升级或验收流程的规范文档。
7. 任何面向人类主管长期阅读、用于快速理解项目全局资产的指导文档。

以下内容【绝对禁止】套用本规范（包括绝对禁止添加元信息头部、章节坐标与导读定位），必须直接保持物理裸文本状态：

1. 一次性命令终端输出。
2. 临时产生的报错日志与调试信息。
3. 开发过程中的临时中间草稿与构思片段。
4. 不进入知识库的短期 scratch 记录。
5. 用户当轮直接在聊天框中提供、仅用于本轮临时分析的截图、代码片段或原始数据。

### 8.3 文档头部元信息（全分类绝对统一标准模板）

凡经人类主管指定需要走本规范入库的 Markdown 文档，开头必须无条件使用以下轻量元信息标准模板。无论是面向机器的 `Aider-facing` 还是面向人类的 `Human-facing` 文档，以下 7 个核心基础字段均为底线钢筋，**严禁进行任何形式的删减、隐藏、随意合并或重命名**：

```markdown
- 文档主受众：[Aider-facing / Human-facing / Architect-RAG-facing / Hybrid-Control]
- 知识库用途：[项目摘要 / 当前任务 / 参考架构 / 侦察证据 / 方法规范 / Aider 规范 / 人类导读]
- 文档状态：[正式版 / 草案 / 当前有效 / 历史归档 / 待确认 / 已废弃]
- 最高依据：[凡涉及具体技术蓝图，必须无条件指向 UniMesh_Architecture_Plan.md，否则填写“无”]
- 事实边界：[显式说明本文档不能被如何误用，哪些是已确认事实，哪些仅属于解释性说明或待确认事项]
- 主要用途：[本文档主要服务什么具体任务或理解目标]
- 场外架构师检索用途：[本文档进入知识库后，主要帮助场外架构师在遇到什么问题时召回什么上下文]
```

*注：对于 Aider-facing 或 Hybrid-Control 文档，可在该标准模板最下方增补 `Aider 执行用途`、`修改前置条件` 或 `验收标准` 等扩展行；对于 Human-facing 文档，可在下方增补 `人类阅读用途` 或 `适用范围` 行；但上方的 7 个核心基础字段的位置、命名与顺序必须保持绝对一致。元信息头部必须准确客观，Aider 严禁伪造关联文档、伪造状态或伪造已确认事实。*

### 8.4 不同主受众的写作策略

- **Aider-facing 文档**：必须保留高密度技术细节、执行纪律、严格规范、开发步骤、提示词模板、验收标准和禁止事项；RAG 索引用于帮助场外架构师理解 Aider 当前受哪些规则约束，并据此生成下一轮精确指令。Aider 严禁为了人类阅读的流畅性而删减任何代码车间执行约束。
- **Human-facing 文档**：必须优先服务人类主管快速理解项目结构、总体流程、阶段进展、概念关系和设计取舍。语言应清晰、规范、直观，避免不必要的晦涩表达。可以加入轻量 RAG 索引，但【绝对禁止】让机器索引和繁余标签污染人类主管的自然阅读体验。严禁把人类导读说明伪写成正式技术蓝图或源码实现事实。
- **Architect-RAG-facing 文档**：必须优先保证文档级索引、章节坐标、本节摘要、事实状态、面包屑路径、触发问题和使用限制，以全力支持场外架构师通过知识库检索准确恢复项目状态、当前任务、历史结论和事实边界，彻底消除幻觉。
- **Hybrid-Control 文档**：必须采用“技术控制内容完整 + 人类导读清晰 + RAG 锚点稳定”的三层完整表达。严禁写成只有机器索引、缺少实质技术内容的空壳；也严禁写成只有高密技术细节、缺少人类导读和检索锚点的长文。

### 8.5 章节索引强度分级

Aider 不得机械、盲目地给每个小节、每个表格行、每个短段落都堆砌机器坐标。应根据文档主受众和章节重要性实施严格的刚性截断：

- **高强度索引**：适用于 Aider-facing 关键规范文档、Hybrid-Control 阶段控制文档、当前任务控制文档、架构白皮书、源码侦察报告、参考工程分析、验收矩阵以及 `UniMesh_Architecture_Plan.md` 等最高蓝图类文档。必须完整包含标准元信息头部、章节坐标、本节摘要与事实状态标记。
- **中等或低强度索引**：适用于 `Project_Tree.md` 这类面向人类的项目总体规划和研发流程文档、`History.md` 历史记忆归档文档，以及面向人类但会进入知识库的阶段总结文档。只允许包含标准元信息头部、二级标题大节开头的轻量导读定位与本节摘要。
- **无索引**：适用于所有未被主管指明要走本规范的临时日志、报错输出、当轮截图分析与短期 scratch 草稿。

### 8.6 章节坐标与导读定位（刚性截断限制）

对于高强度索引文档，每个重要二级或三级章节开头应加入完整章节坐标块：

> **章节坐标**：[知识库用途] / [文档名] / [上级章节] / [当前章节]
> **Aider 执行用途**：[如果适用，本节对 Aider 的具体约束、任务或操作意义]
> **人类阅读用途**：[如果适用，本节帮助人类主管理解什么]
> **场外架构师检索用途**：[本节被 RAG 召回后帮助场外架构师判断什么]
> **触发问题**：[用户或场外架构师提出哪些问题时应优先召回本节]
> **事实状态**：[正式定义 / 已确认事实 / 当前任务 / 架构推断 / 待源码确认 / 历史归档 / 解释性说明]
> **使用限制**：[本节不能被如何误用]

对于 Human-facing 文档，应使用轻量导读定位：

> **导读定位**：[文档名] / [当前章节]
> **本节回答**：[本节主要帮助人类主管理解的问题]
> **检索用途**：[进入知识库后，本节可帮助场外架构师召回的内容]
> **事实边界**：[已确认 / 解释性说明 / 待确认 / 禁止误用]

**【全项目刚性限制红线】对于 `Human-facing` 和人类导读类的长期文档（如 `Project_Tree.md`），上述导读定位【仅允许】加在二级标题（`##`）及以上的大章节开头。三级标题（`###`）及以下、正文自然段、短列表或任何表格行内部【绝对禁止】插入任何机器坐标或定位标志，必须保持绝对纯净，严禁逐行污染阅读体验！**

### 8.7 本节摘要

对于较长章节，Aider 应在标题与坐标下方加入“本节摘要”。摘要强度必须根据文档主受众实施定向调整：

- **Aider-facing / Hybrid-Control 摘要**：应精确概括本节对 Aider 的执行意义、技术约束、验收要求、与 UniMesh 架构或当前任务的关系、事实边界和使用限制。
- **Human-facing 摘要**：应说明本节帮助人类主管理解什么、为什么重要、它在项目全局中的位置、哪些内容是已确认事实、哪些只是解释性说明或待确认事项。

推荐格式：

#### 本节摘要
用 3～6 句话概括本节核心内容，说明本节的主要用途、项目位置、事实边界和使用限制。不得新增未经确认的事实，不得把阶段计划写成已完成，不得把架构判断写成源码实现事实。

本节摘要必须自然包含稳定关键词，便于知识库切块检索；但 Human-facing 文档不得为了检索而堆砌生硬重复的关键词。

### 8.8 事实状态标记

凡涉及项目状态、源码事实、架构定义、任务计划、验收结论、Aider 执行边界、人类导读结论的内容，在高强度索引文档中必须尽量使用事实状态标记。事实状态标记是防止 Aider 误执行、防止场外架构师误召回、防止人类主管误解项目状态的核心防线。

推荐格式：

#### 事实状态
- **已确认**：...
- **正式定义**：...
- **当前任务**：...
- **解释性说明**：...
- **待确认**：...
- **当前推断**：...
- **历史归档**：...
- **禁止误用**：...

局部条目标记示例：
- 【已确认】UniMesh 已建立 `Project_Tree.md` 和 `UniMesh_Architecture_Plan.md`。
- 【正式定义】具体技术蓝图以 `UniMesh_Architecture_Plan.md` 为最高依据。
- 【解释性说明】本段用于帮助人类主管理解架构关系，不等价于新增技术蓝图。
- 【当前任务】本阶段 Aider 应优先执行用户指定的当前侦察或文档同步任务。
- 【待源码确认】某参考工程的具体接口细节仍需后续只读侦察。
- 【历史归档】本条记录仅说明过去完成的阶段，不代表当前仍是优先任务。
- 【禁止误用】不得将本文档中的架构抽象直接等同于已完成源码实现。

Aider 严禁把“待确认”、“推断”、“计划”、“建议”、“解释性说明”、“历史归档”改写成“已完成”、“已实现”、“已验证”或“当前任务”。

### 8.9 面包屑路径

长文档中的关键片段应尽量保留面包屑路径，尤其是容易被知识库切块拆散的章节。面包屑路径用于保证片段被知识库单独召回时，仍然能够自洽呈现其位于哪个文档、哪个阶段、哪个主题下。

推荐格式：
> **路径**：[知识库用途] / [文档名] / [一级主题] / [二级主题] / [当前小节]

示例：
> **路径**：项目摘要 / `Project_Tree.md` / 人类导读 / UniMesh 研发演进图谱

对于 Aider-facing、Architect-RAG-facing 和 Hybrid-Control 文档，应在关键章节稳定使用面包屑路径。对于 Human-facing 文档，面包屑路径已完全被二级标题处的“导读定位”所合并替代，严禁滥用。

### 8.10 稳定关键词与同义词控制

Aider 必须保持 UniMesh 已固化术语稳定，不得随意改写正式命名。重要术语首次出现时，应给出必要说明。对同一概念，不得在同一文档中反复使用多个不一致名称。对 RAG 检索高价值关键词，应在标题、摘要、章节坐标和正文中自然重复。

高价值关键词白名单包括但不限于：
UniMesh；M3DC1；TOKAMAKER；TRIMEG；GenericSim；`UniMesh_Architecture_Plan.md`；`Project_Tree.md`；`CONTEXT.md`；`History.md`；Layer；核心层；生成层；驱动层；适配器架构；中立网格内核；驱动插件体系；驱动层适配；三源接口基线对齐；蓝图驱动开发；当前任务；项目摘要；Aider 侦察；场外架构师；RAG；知识库；人类导读；已确认；正式定义；解释性说明；待确认；历史归档；禁止误用；只读隔离；下游源码。

Human-facing 文档应自然使用关键词，不得为了检索而堆砌生硬重复。凡涉及具体接口、目录、文件职责、关键字清单和数值实现规范时，必须回到 `UniMesh_Architecture_Plan.md` 对齐，不得凭上下文自行补全。

### 8.11 切块友好写法（避坑消除含混代称）

Aider 生成进入知识库的文档时，应假设知识库会将长文档切成 800 字左右的独立片段。因此每个较完整的语义块都应尽量自洽。

Aider-facing / Hybrid-Control 语义块最好包含：当前主题、所属文档或章节、对 Aider 的执行意义、对场外架构师的检索意义、与项目全局的关系、事实状态、当前用途、使用限制。

Human-facing 语义块最好包含：当前主题、它在项目全局中的位置、它帮助人类主管理解的问题、事实边界、与正式蓝图或源码证据的关系。

**【严重错误表达】**：
> “如上所述，本层继续承担这些职责。”

**【规范化推荐写法】**：
> “Layer N 在 UniMesh 架构中的职责必须以 `UniMesh_Architecture_Plan.md` 为最高依据。本节用于帮助人类主管理解该层在当前项目阶段中的架构定位，同时为场外架构师提供可检索的上下文；该定位不代表相关源码实现已经完成。”

RAG 切块后，“如上所述”、“这些职责”、“该模块”等含混指代会彻底失去上文，导致场外架构师产生严重误判，也会导致人类主管或 Aider 后续理解偏离。

### 8.12 针对 `Project_Tree.md` 的轻量索引策略

`Project_Tree.md` 属于标准的 Human-facing 文档，主要服务人类主管快速查看 UniMesh 仓库结构、目录职责、总体开发流程、BFS 研发路线和验收防线。该文档进入知识库后，主要用于场外架构师召回项目目录结构、开发流程、层级路线、只读参考库定位和阶段性验收防线，【绝对不得】改造成高密度的机器索引文档。

`Project_Tree.md` 仅允许在【顶层目录结构、src/ 源码目录结构、蓝图驱动开发协议、项目研发演进图谱、黑箱验收指标】这 5 个核心大节（二级标题 `##`）开头添加轻量导读定位。

**【刚性禁令】**：Aider【绝对禁止】在顶层目录说明表格中的每一行、`src/core/` 目录说明表格中的每一行、`src/drivers/` 目录说明表格中的每一行或任何短列表与表格行内部添加机器索引，优先保证人类主管直观阅读的极佳流畅度！

`Project_Tree.md` 中若提及 `STUDIO_CONTEXT.md`，必须采用刚性防御性表述，禁止 Aider 触碰。例如：
```markdown
| `STUDIO_CONTEXT.md` | 场外架构协作专用上下文文件，仅供人类主管与场外架构师使用；代码车间 AI 不得读取、修改、写入或展开讨论。 |
```

### 8.13 当前任务类文档的特殊要求

当前任务类文档通常属于 Hybrid-Control 文档，必须同时服务 Aider 执行、人类主管审阅和场外架构师 RAG 检索。文档开头必须明确：

```markdown
# 当前任务：[任务名称]

- 文档主受众：Hybrid-Control
- 知识库用途：当前任务
- 文档状态：[当前有效 / 历史归档]
- 最高依据：UniMesh_Architecture_Plan.md
- 事实边界：[明确指明本任务所处的层级边界与禁止事项]
- 主要用途：[指导 Aider 执行当轮开发与验收]
- 场外架构师检索用途：[帮助场外架构师对齐当前开发进度与验收约束]
```

除头部元信息外，文档正文必须清晰包含以下小节：
- **当前目标**：用一句话说明本任务要攻克的阵地。
- **当前优先级**：说明本任务在当前 Layer 中的顺序。
- **下一步 Aider 动作**：明确下达对 Aider 的具体操作指令。
- **当前输出要求**：规定 Aider 交付时必须提交的代码、测试或文档修改。
- **验收标准**：列出量化或可测试的通过条件。
- **当前禁止事项**：列出 Aider 本轮严禁触碰的红线。
- **失效条件与历史归档规则**：说明本任务何时完成并转换为归档状态。

当前任务类文档必须明确哪些内容是“当前仍有效”，哪些内容是“历史归档”。如果任务阶段切换，应即时更新文档状态，严禁让旧任务伪装成当前任务。当前任务严禁与长期项目摘要混杂，避免 RAG 检索时把历史任务误召回为当前有效证据。

### 8.14 项目摘要类文档的特殊要求

项目摘要类文档通常属于 Hybrid-Control 或 Architect-RAG-facing 文档，主要帮助场外架构师恢复项目全局状态，同时也帮助 Aider 对齐长期开发边界，并协助人类主管快速回顾项目进展。项目摘要类文档必须明确：

- 项目总体目标与工程定位。
- 当前阶段定位与已完成里程碑。
- 正式层级定义与长期研发路线。
- 已确认事项与未确认事项清单。
- 当前仍有效的工程纪律与禁止误用事项。
- 与 `UniMesh_Architecture_Plan.md` 的继承与依赖关系。

项目摘要类文档应优先回答以下核心宏观问题：
1. 我们当前做到哪一步了？
2. 某个 Layer 的正式定义是什么？
3. 当前长期主线是什么？哪些成果已经完成？
4. 哪些事项仍待后续蓝图或源码确认？
5. Aider 在后续任务中必须遵守哪些长期物理边界？

**【红线纪律】**：项目摘要类文档严禁承载 `UniMesh_Architecture_Plan.md` 独占的具体技术蓝图细节。凡涉及具体组件接口、目录树职责、核心层允许/禁止概念、驱动层私有映射边界、下游数值约束和详细实现规范，必须无条件指向 `UniMesh_Architecture_Plan.md`，绝对禁止在摘要文档中私自复制、篡改或替代！

### 8.15 Aider 执行规范类文档的特殊要求

Aider 执行规范类文档属于 Aider-facing 或 Hybrid-Control 文档，必须保留高密度严格规范、禁止事项、执行步骤、验收标准和提示词模板。此类文档进入知识库后，主要用于场外架构师理解 Aider 当前受哪些规则约束，并据此为人类主管生成更精确的下一轮 Aider 调度指令。

Aider 执行规范类文档正文必须清晰界定：
- 当前规范约束的任务具体类型。
- **Aider 可以做什么**（正面授权范围）。
- **Aider 不可以做什么**（负面禁止清单）。
- 执行前必须先查阅并对齐哪些基础文件。
- 哪些文件属于只读隔离区，哪些文件属于架构最高依据。
- 修改相关代码或文档的前置条件与自检验收流程。
- 触发向 `History.md` 写入历史战果的具体条件。
- 严禁触碰的文件与目录清单（如 `STUDIO_CONTEXT.md` 与外部参考库）。

Aider 执行规范类文档绝不允许被简化或概括为泛泛的高阶原则！其核心工程价值在于以铁律约束具体的机器执行行为，因此必须保持极高的规则密度与强约束力。

### 8.16 人类导读类文档的特殊要求

人类导读类文档属于 Human-facing 文档，主要服务人类主管快速理解 UniMesh 项目的结构、目标、路线、阶段状态、概念关系和设计取舍。此类文档应严格遵守 `CONTEXT.md` 中的人机协同知识反哺协议，使用清晰、标准、直观的工业学术语言组织说明，坚决避免不必要的晦涩表达与堆砌。

人类导读类文档正文必须清晰交代：
- 本文档主要帮助人类主管理解什么核心概念或进度。
- 当前主题在 UniMesh 总体架构图谱中的物理位置。
- 与正式单事实源蓝图 `UniMesh_Architecture_Plan.md` 的对齐关系。
- 明确圈定哪些内容是已确认事实，哪些仅属于辅助性解释说明。
- 明确圈定哪些内容仍待后续源码探查或蓝图终审确认。
- 显式声明本文档进入知识库后，场外架构师可通过它召回什么宏观上下文。

人类导读类文档推荐采用轻量索引，拒绝冗余机器化标志。推荐标准结构：

```markdown
# [人类导读大标题]

- 文档主受众：Human-facing
- 知识库用途：人类导读 / 项目摘要
- 文档状态：[正式版 / 当前有效 / 历史归档]
- 最高依据：UniMesh_Architecture_Plan.md
- 事实边界：[明确说明本文档用于帮助人类理解，不承载具体技术蓝图细节]
- 主要用途：[帮助人类主管快速把握某模块或某阶段的架构理念]
- 场外架构师检索用途：[帮助场外架构师召回项目研发演进图谱与宏观导读认知]

## [大章节标题]

> **导读定位**：[文档名] / [当前大章节]
> **本节回答**：[人类主管读完本节应掌握什么核心认知]
> **事实边界**：[已确认 / 解释性说明 / 待确认 / 禁止误用]

#### 本节摘要
...

#### 直观说明与架构解析
...

#### 与 UniMesh 全局的映射关系
...
```

人类导读类文档严禁堆砌 Aider 底层执行细节，严禁将面向 Aider 的严格提示词模板混入正文，除非该文档被人类主管明确标注为 Hybrid-Control。

### 8.17 参考工程白皮书和侦察报告的特殊要求

参考工程白皮书、源码侦察报告、路径索引分析文档通常属于 Hybrid-Control 文档，必须同时支持 Aider 的后续只读侦察、人类主管理解参考工程定位以及场外架构师的 RAG 检索。

此类文档在编写时，必须在结构上严格进行事实分层隔离：
1. **官方文档已确认内容**：来自参考工程官方手册或论文的客观描述。
2. **源码路径索引证据**：明确标注源码文件路径、行号与核心数据结构命名的绝对事实。
3. **Aider 只读侦察结论**：Aider 在主管指挥下通过检索阅读得出的结构化总结。
4. **架构推断与对齐建议**：关于如何把参考工程的网格能力映射为 UniMesh 通用插件体系的分析。
5. **后续待侦察入口**：列出下一轮需要深入探查的源文件或函数指针。
6. **禁止误用红线**：显式说明外部参考源码处于只读隔离区，严禁篡改。

**【核心纪律】**：严禁把外部参考工程中的事实直接等同于 UniMesh 已实现的通用功能！所有“可对齐”、“可覆盖”、“可适配”的表述必须显式说明这是架构判断、接口推断还是已落地的源码事实。`M3DC1`、`TRIMEG`、`TOKAMAKER` 等外部参考源码依旧属于绝对只读隔离区，严禁通过编写侦察报告暗示或诱导 Aider 去修改其官方底层源码。

### 8.18 Hybrid-Control 文档的特殊要求

Hybrid-Control 文档是 UniMesh 项目中至关重要的控制文档类型，既要对 Aider 有刚性执行约束，又要对人类主管有极佳的审阅价值，同时还要对场外架构师有精准的 RAG 检索锚点。Aider 生成或修改 Hybrid-Control 文档时，必须必须采用“三层工整结构”：

1. **技术控制层**：完整保留 Aider 编码与调试所需的高密技术细节、执行纪律、严格规范、提示词模板和量化验收标准。
2. **人类导读层**：通过标题配置、清晰摘要、对齐表格与直观说明，大幅降低人类主管的阅读与审阅负担。
3. **RAG 索引层**：通过标准元信息头部、二级标题章节坐标、事实状态、触发问题、面包屑路径和使用限制，完美服务场外架构师的冷记忆召回。

推荐 Hybrid-Control 章节标准结构：

```markdown
## [大章节标题]

> **章节坐标**：[知识库用途] / [文档名] / [当前章节]
> **Aider 执行用途**：[本节指导或约束 Aider 编码与验收的具体内容]
> **人类阅读用途**：[本节帮助人类主管快速审阅的设计取舍与阶段进展]
> **场外架构师检索用途**：[本节被 RAG 召回后提供的技术锚点与进度状态]
> **触发问题**：[何种架构讨论或报错追溯应优选召回本节]
> **事实状态**：[正式定义 / 已确认事实 / 当前任务 / 历史归档]
> **使用限制**：[显式说明本节不能被如何误用或跨层外溢]

#### 本节摘要
...

#### 人类导读与架构背景
...

#### 技术控制规范与细节
...

#### Aider 刚性执行要求与验收准则
...
```

Hybrid-Control 文档严禁写成只有机器标签、缺少实质技术细节的空壳；也严禁写成只有生硬代码与指令、缺少人类导读与检索坐标的混乱长文。

### 8.19 知识库用途白名单枚举（收归人类主管掌控）

凡经主管指定需要走本规范入库的 Markdown 文档，其头部标准模板中的 `知识库用途：` 字段，必须且只能从以下明确的白名单中选择一项，**已彻底废除并抹去“不入库”这一具有逻辑死锁与噪声污染的过时标签**：

- **项目摘要**：用于中长期控制、大局规划、里程碑总揽及层级定义文档。
- **当前任务**：用于主管下发的当前阶段控制文档、Aider 任务清单与验收要求。
- **参考架构**：用于核心单事实源总蓝图 `UniMesh_Architecture_Plan.md`。
- **侦察证据**：用于源码侦察报告、路径索引分析、参考工程调研成果。
- **方法规范**：用于长期开发纪律、黑箱 Bug 防御和回归测试规范。
- **Aider 规范**：用于直接约束和指导 Aider 编码行为的硬核规范。
- **人类导读**：用于专供人类主管渐进式理解项目全局的导读、概念解释文档。

### 8.20 禁止事项（全项目高压红线）

Aider 在生成、重构、归档或修改技术文档时，绝对禁止以下违规行为：

1. **禁止自发妄动**：严禁自发、擅自为任何未被人类主管指明走第 8 条规范的临时文件生成元信息头部或坐标。
2. **禁止形式主义**：严禁把四类受众标签当成强制目录分类体系而机械创建冗余文件夹；严禁对一次性日志和短期 scratch 记录强制套用模板。
3. **禁止污染可读性**：严禁破坏 Human-facing 文档的自然阅读流畅度；严禁在二级标题（`##`）以下的三级标题、短段落或表格行中逐行堆砌机器索引与坐标。
4. **禁止模板漏项**：严禁移除或删减基础头部标准模板中的 `最高依据`、`事实边界` 等 7 个核心底线字段。
5. **禁止含混代称**：严禁为了行文省事而使用“如上所述”、“前述内容”、“该模块”、“这些东西”等依赖前后文的含混指代，确保片段切块后的绝对自洽。
6. **禁止事实篡权**：严禁把“待确认”、“推断”、“计划”、“建议”、“解释性说明”、“历史归档”擅自改写成已完成、已验证的“源码实现事实”。
7. **禁止架构漂移**：严禁为了让文档“看起来完整”而私自补写未经蓝图或源码证据支持的组件接口、目录职责或数值规范；严禁复制或篡改 `UniMesh_Architecture_Plan.md` 独占承载的技术蓝图细节。
8. **禁止触碰禁区**：严禁以任何形式读取、修改、写入或展开讨论 `STUDIO_CONTEXT.md`；严禁修改 `M3DC1`、`TRIMEG`、`TOKAMAKER` 等只读参考库中的任何源码。
9. **禁止术语混乱**：严禁擅自改写或创造 UniMesh 已固化核心术语、Layer 层级定义或文档核心定位。
10. **禁止定位颠倒**：严禁将面向场外架构师的 RAG 索引误当成替代 Aider 技术细节的理由；严禁将面向人类主管的导读说明误当成正式技术蓝图。

### 8.21 文档修改时的最低自检与验收标准

每次 Aider 在人类主管指挥下完成重要 Markdown 文档的重构或迭代后，必须严格对照以下清单执行结构与质量自检。对于 Human-facing 文档，可按照轻量策略适当简化机器索引项；对于 Aider-facing、Architect-RAG-facing 和 Hybrid-Control 文档，必须完整执行100%覆盖自检：

```markdown
## RAG / 技术文档结构与质量全流程自检清单

- [ ] 该文档是否由人类主管明确下达指令要求进行第 8 条规范迭代？（若无，立刻退出并保持裸文本状态）
- [ ] 长期入库文档开头是否无条件使用了全分类绝对统一的标准元信息头部模板？
- [ ] 标准元信息头部的 7 个核心基础字段（包含最高依据、事实边界等）是否完整未删减、未重命名？
- [ ] 若为 Human-facing 或人类导读文档，机器索引与定位是否【绝对严格圈定】在二级标题（##）及以上，毫无逐行污染？
- [ ] 是否彻底消灭了“如上所述”、“这些职责”、“前述模块”等依赖上下文的含混代称，保证了切块自洽？
- [ ] 是否严格划分了“已确认”与“待确认”的事实状态，绝无将蓝图计划或架构解释伪写成已落地的源码事实？
- [ ] 关键工程术语（如适配器架构、中立网格内核、三源接口基线对齐、蓝图驱动开发等）在正文中是否保持高度一致？
- [ ] 涉及具体类职责、模块接口与实现细节时，最高依据是否无条件指向了 UniMesh_Architecture_Plan.md？
- [ ] 是否严格守住了物理隔离防线，绝未触碰 STUDIO_CONTEXT.md 与任何只读参考工程源码？
- [ ] 是否保留了该文档主受众所需的完整内容密度（即 Aider-facing 细节饱满、Human-facing 清爽直观）？
```

本规范长期有效，作为 UniMesh 工程体系的基础法律支柱。Aider 必须把它视为保障项目冷记忆纯净度、防止事实幻觉与维护人机协同纪律的最高质量防线，严格服从人类主管对全系统记忆资产的绝对指挥权。
